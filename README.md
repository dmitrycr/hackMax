# HackMax — «До подачи»

Каркас сервиса предварительной проверки документов в MAX.
**Go** управляет приложением и правилами, **Python** читает документы и выполняет
OCR, **React** предоставляет мини-приложение и кабинет методиста.

## Текущее состояние

Это инфраструктурный каркас. Реализованы:

- экран состояния на React / TypeScript / MAX UI;
- Go API: `/healthz`, `/readyz`, `/api/v1/system`;
- подключение PostgreSQL, миграции приложения и River;
- Go worker с реальным заданием проверки доступности Python;
- отдельный текстовый эхо-бот MAX с запуском через `cmd/bot`;
- клиент бесплатных моделей OpenRouter, модуль смысловой проверки и тестовое
  задание на синтетическом тексте (нужен API-ключ);
- проверка дословных цитат `semantic-v2` и команда оценки качества на восьми
  синтетических примерах с JSON-отчётом и сравнением моделей;
- внутренний FastAPI с проверкой сервисного токена;
- контракт будущего извлечения документов;
- Docker Compose, локальные секреты, lock-файлы, проверки и CI.

**Следующий этап:** вход через MAX, загрузка файлов, версии комплектов,
извлечение DOCX/PDF, OCR, правила ведомства, замечания и экспорт.
Пакеты для этих областей выделены, но предметная логика ещё не реализована.
`POST /internal/v1/extract` намеренно возвращает **501 `extraction_not_implemented`**.
Установленные библиотеки OCR не означают готовую проверку сканов.

## Быстрый запуск

Нужны Docker с Compose, Python 3 для создания `.env` и `make`.

```sh
make up
```

Команда создаёт `.env` со случайными локальными секретами, собирает образы,
выполняет миграции и запускает компоненты. Существующий `.env` не перезаписывается.
Первая сборка скачивает образы и зависимости и может занять несколько минут.

Открыть **http://localhost:8080**. Порты привязаны к `127.0.0.1`.

```sh
make probe           # Реальная проверка PostgreSQL → River → Go worker → Python
docker compose ps    # Состояние контейнеров
make logs            # Журналы сервисов
make down            # Остановка; постоянные тома сохраняются
```

Для мини-приложения MAX потребуются публичный HTTPS-домен и регистрация бота.
Эхо-бот использует long polling и может запускаться локально без входящего HTTPS.
Текущая конфигурация предназначена для локальной разработки. `GATEWAY_ADDRESS`
подготовлен для Caddy, но одного изменения адреса недостаточно: нужно настроить
DNS, доступные порты и авторизацию. У Go worker уже есть исходящая сеть для
OpenRouter; эхо-бот использует отдельную исходящую сеть, а авторизация мини-приложения
MAX ещё не реализована.

## LLM через OpenRouter

В локальный `.env` добавьте `OPENROUTER_API_KEY` и
`OPENROUTER_MODEL=openrouter/free`, затем выполните `make up` и `make probe-llm`.
В Docker ключ получает только Go worker; локальная команда оценки также читает
его из `.env`. Можно закрепить конкретную модель `provider/model:free`.
Платные модели отклоняются клиентом; перехода на платную модель при сбое нет.
Без ключа остальной каркас работает, а LLM-проверка недоступна.
Команда отправляет синтетический пример и проверяет JSON-ответ, источники и цитаты;
она не сравнивает смысловой результат с эталоном. Пользовательская загрузка и
сохранение результатов в БД ещё впереди.

### Проверка цитат и ошибок модели

Ответ `semantic-v2` содержит `evidence: [{source_id, quote}]`. Цитата должна
присутствовать в указанном фрагменте; нормализуются только пробелы и переносы.
Допускается несколько источников. Выдуманная цитата, неизвестный источник или
нарушенный контракт вызывают `model_output_error`: такие замечания не показываются
как ошибки документа. Недостаток исходного контекста — отдельный результат
`insufficient_data`. Флаг `context_complete` устанавливает вызывающая система,
а не текст документа. В промпте запрещено придумывать факты, суммы и сроки для исправлений.

### Оценка качества

```sh
make eval-llm
```

Нужны Go и ключ OpenRouter в `.env`; Docker, БД и бот не требуются. Команда делает
8 запросов на синтетическом наборе и сохраняет ответы и сводку в
`data/evaluations/latest.json` (не коммитится). Сравниваются статусы и источники;
отдельно учитываются пропуски, ложные замечания, ошибки API и неподтверждённые ответы.
Лимиты запросов остаются `OPENROUTER_TIMEOUT=180s` и `OPENROUTER_MAX_TOKENS=8000`.

Сравнение двух моделей (из `services/backend`):

```sh
go run ./cmd/eval-llm -env-file ../../.env \
  -models liquid/lfm-2.5-2.6b:free,nvidia/nemotron-3-super-120b-a12b:free \
  -out ../../data/evaluations/model-comparison.json
```

`-repeat 3` повторяет каждый случай трижды и позволяет увидеть изменения статусов
и источников. Это увеличивает расход бесплатной квоты. Ошибка или расхождение
дают ненулевой код завершения; отчёт сохраняется после каждого запроса.

Даже 8/8 не доказывает правильность толкования всех документов: это небольшой
набор для разработки, без независимой экспертной проверки. Цитаты подтверждают
происхождение текста, а рекомендации и обоснованность выводов нужно читать отдельно.
Подробнее: [метрики, ограничения и запуск](docs/llm-evaluation.md),
[контрольный набор](tests/fixtures/llm/README.md).

Первый прогон 22.09.2026: LFM — 8/8 автоматических проверок, NVIDIA — 7/8
и одна ошибка провайдера `503`. Ручная проверка обнаружила недостатки рекомендаций
даже у прошедших ответов. [Результаты и предварительный выбор модели](docs/llm-baseline.md).

## Эхо-бот MAX

Укажите `MAX_BOT_TOKEN` в корневом `.env`, затем выберите один способ запуска:

```sh
make bot-local  # Go на компьютере; загружает корневой .env; остановка Ctrl+C
make bot        # Docker: отдельный сервис в профиле bot
```

Не запускайте оба варианта одновременно с одним токеном. Бот отвечает `Эхо: <текст>`
в тот же чат, а при отсутствии ChatId — отправителю. Для сообщений без текста
возвращает `[сообщение без текста или вложение]`. Сообщения от ботов пропускаются.
Для Docker: `docker compose logs -f bot`, остановка — `make bot-stop`.
Обычный `make up` не запускает профиль bot. Бот не требует PostgreSQL или Python.
Вручную из `services/backend`: `go run ./cmd/bot -env-file ../../.env`.
Без `-env-file` читается только окружение процесса. Переменные окружения имеют
приоритет над `.env`. Токен передаётся только сервису bot.

Корневой сертификат Минцифры встроен в бинарник через `go:embed` и добавляется
к системным доверенным сертификатам только для HTTP-клиента MAX. Проверка цепочки
и имени сервера включена при `MAX_INSECURE_SKIP_VERIFY=false` (по умолчанию).
Для Docker сертификат уже находится в бинарнике, установка в ОС не требуется.
Источник, срок и отпечаток: [описание сертификата](services/backend/internal/integrations/max/certs/README.md).
После обновления кода перезапустите `make bot-local` либо пересоберите через `make bot`.
Старый обход `MAX_INSECURE_SKIP_VERIFY=true` сохранён для явной диагностики,
но для обычного запуска больше не нужен. Общий транспорт Go и OpenRouter не меняются.
При ошибке первого GetBot бот пишет предупреждение и продолжает long polling;
успешное подключение логируется только при успешном ответе GetBot.

## Команды разработчика

Локальные инструменты: Go 1.25+, Python 3.12, uv 0.11.6, Node.js 22.12+ и npm.
Точные версии библиотек записаны в `go.sum`, `uv.lock`, `package-lock.json`.

```sh
make check               # Go-тесты/vet, Python lint/тесты, сборка UI, проверка Compose
make generate-contracts  # Экспорт схем из Python-кода
make sqlc                # Генерация Go-методов из SQL через sqlc 1.29.0
```

Изменение Python-контракта требует обновления экспортированных файлов; CI
проверяет, что генерация не оставляет различий. OpenAPI описывает текущий HTTP 501;
`extraction-result.schema.json` описывает планируемый результат, пока не возвращаемый API.

Для разработки UI с горячим обновлением, при уже запущенном Compose:

```sh
cd apps/web
npm ci
npm run dev
```

Vite перенаправляет `/api` на `127.0.0.1:8080`. Браузер не получает токены MAX
или Python. Полные документы и персональные данные не добавляются в Git.

## Проверки перед развитием бизнес-логики

1. Подключить серверную проверку данных запуска MAX и доступ к собственным комплектам.
2. Реализовать закрытое хранилище, ограничения загрузки, версии и удаление файлов.
3. Добавить один профиль DOCX в Python и сквозной вызов из Go worker.
4. Добавить одно подтверждённое правило на Go и привязать замечание к исходному полю.
5. Расширять контрольный набор, затем подключать PDF и OCR отдельными профилями.

Архитектура заложена; создание каркаса не подтверждает качество OCR или
соответствие документов требованиям ведомства.
