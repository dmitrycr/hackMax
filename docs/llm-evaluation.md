# Оценка LLM и проверка цитат

## Что реализовано

`semantic-v2` возвращает `evidence: [{source_id, quote}]` вместо `source_ids`.
Каждое требование рассматривается ровно один раз. Для `met` и `needs_review`
нужна хотя бы одна цитата; для противоречий промпт требует обе стороны.
Количество нужных доказательств в предметном смысле проверяет контрольный набор,
а универсальный валидатор проверяет только наличие и принадлежность цитат.

Цитата сопоставляется с указанным фрагментом после схлопывания пробелов и переносов.
Регистр, отрицания, цифры, пунктуация и алфавит сохраняются. OCR в цитате не исправляется.
Совпадение цитаты доказывает её происхождение, но не истинность вывода.

`context_complete` в требовании устанавливает вызывающая система. Если весь
релевантный раздел не передан, отсутствие подтверждения не равно нарушению.
Это различие закреплено в промпте и примерах; автоматического доказательства
полноты и правильности интерпретации пока нет.

Ошибки структуры и цитат возвращаются как `model_output_error`, а не как
`needs_review`. При такой ошибке весь набор замечаний отклоняется; сохраняются
доступные метаданные модели/токенов, но не неподтверждённые замечания или сырой ответ.
`insufficient_data` — нормальный содержательный результат, отличный от сбоя API.

## Два разных запуска

`make probe-llm` — техническая проверка River → worker → OpenRouter.
Её успех не означает совпадение с эталоном.

`make eval-llm` — оценка на восьми синтетических примерах. Она вызывает тот же
пакет `semantic`, но напрямую, без БД, очереди и MAX. Нужны Go и ключ в `.env`.
Будет сделано восемь внешних запросов к выбранной бесплатной модели, без автоповторов.

```sh
make eval-llm
```

Отчёт: `data/evaluations/latest.json` (исключён из Git). Он содержит принятые
ответы с цитатами и рекомендациями, ожидаемые результаты, ошибки, фактическую
модель, версию промпта, версию и SHA-256 набора, время и расход токенов.
Отчёт обновляется после каждого запроса, поэтому завершённые результаты сохранятся
при прерывании следующего вызова.

Сравнение моделей из `services/backend`:

```sh
go run ./cmd/eval-llm -env-file ../../.env \
  -models liquid/lfm-2.5-2.6b:free,nvidia/nemotron-3-super-120b-a12b:free \
  -out ../../data/evaluations/model-comparison.json
```

Доступность конкретных ID меняется; ошибка API не доказывает плохое смысловое
качество модели. `openrouter/free` может выбирать разные модели для разных случаев.
Группировка отчёта ведётся по запрошенной модели, фактические модели перечислены отдельно.

Для повторов добавьте `-repeat 3`: это утроит число запросов. Интервал по умолчанию
4 секунды, меняется через `-interval`. Он не заменяет общий ограничитель квоты.
Лимиты 180 секунд и 8000 токенов берутся из существующих настроек OpenRouter.
За один запуск допускается не больше 100 вызовов. На 401/402/429 и сетевом сбое
прогон останавливается; отчёт содержит число запланированных и завершённых вызовов.

## Как читать результат

- `pass`: ожидаемые статусы и набор источников совпали, структура и цитаты проверены.
- `mismatch`: ответ технически пригоден, но расходится с эталоном.
- `model_output_error`: ответ или цитаты не прошли проверку; это не ошибка документа.
- `api_error`: сбой вызова, квота, отказ провайдера или непригодный HTTP-ответ.
- `input_error`: некорректные входные данные (обычно обнаруживаются до запросов).

Команда возвращает ненулевой код при любом расхождении, ошибке или неполном прогоне;
это ожидаемое поведение оценки, а не обязательно неисправность команды.

В сводке:

- `missed_issues`: ожидалось needs_review, получено met;
- `false_issues`: ожидалось met, получено needs_review;
- `unsupported_approvals`: ожидалось insufficient_data, получено met;
- `source_mismatches`: неверный набор источников;
- `status_matches / compared_requirements`: совпадения среди технически пригодных ответов;
- `passed_cases / attempts`: прохождение случаев с учётом технических ошибок;
- `repeated_cases_with_valid_answers` и `cases_with_changed_status_or_sources`: устойчивость повторов.

Переход в insufficient_data вместо требуемого замечания виден как mismatch,
но не включается в узкий показатель missed_issues. Матрицу статусов можно восстановить
из `comparisons` каждого запуска. Ошибки API и невалидные ответы не входят в знаменатель
смысловых сравнений — их долю обязательно смотреть отдельно. Ноль нестабильных
случаев при отсутствии повторов ничего не говорит об устойчивости.

## Ограничения

Это небольшой набор для разработки. Он не подтверждён специалистом ведомства
и не является независимым экзаменом после настройки промпта. Даже 8/8 не доказывает
готовность к реальным документам. Нужны ручная проверка рекомендаций, отдельные
контрольные случаи и повторные прогоны. Автоматического LLM-судьи нет.

Загрузка документов, извлечение/OCR, маскирование, формальные правила и сохранение
пользовательских проверок не реализуются этим этапом. RAG и итоговый балл готовности
также не добавлены.
