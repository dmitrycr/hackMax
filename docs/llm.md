# LLM в MVP: OpenRouter

## Решение и текущая реализация

Go worker вызывает `https://openrouter.ai/api/v1/chat/completions` через `net/http`.
Python отвечает за чтение файлов и OCR, Go — за формальные проверки, LLM — за
смысловое сопоставление с переданными требованиями и объяснение замечаний.

- `internal/integrations/llm`: HTTPS-клиент, тайм-аут по умолчанию 180 секунд, ограничение размера,
  запрет перенаправления ключа, ошибки без текста документов.
- `internal/modules/semantic`: вход, промпт, JSON Schema, проверка покрытия
  требований, ссылок и дословных цитат (`semantic-v2`).
- `internal/evaluation` и `cmd/eval-llm`: оценка на синтетическом наборе с эталонами.
- `internal/jobs/llm_probe.go`: River-задание с синтетическим примером.
- Очередь `llm`: один обработчик на процесс worker, одна попытка на probe.
- В Docker ключ доступен только worker; локальная команда оценки читает его из `.env`.
  Сеть `llm-egress` разрешает исходящие соединения;
  она не ограничивает их одним доменом.

По умолчанию `OPENROUTER_MODEL=openrouter/free` выбирает доступную бесплатную модель.
Для оценки качества нужно закрепить конкретную `provider/model:free` с поддержкой
structured outputs. Результат сохраняет фактическое имя модели; маршрутизатор не
обеспечивает воспроизводимость качества между вызовами.
Клиент отклоняет другие идентификаторы и задаёт нулевой `provider.max_price`
для входных, выходных токенов и запроса. Платные модели, плагины и список запасных
моделей не включены. Если подходящего endpoint нет, запрос завершается ошибкой.

## Подключение

1. Создать ключ в [OpenRouter](https://openrouter.ai/settings/keys).
2. Добавить в локальный `.env` (существующий файл `make setup` не перезаписывает):

   ```dotenv
   OPENROUTER_API_KEY=ваш_ключ
   OPENROUTER_MODEL=openrouter/free
   OPENROUTER_TIMEOUT=180s
   OPENROUTER_MAX_TOKENS=8000
   ```

3. Выполнить `make up`, затем `make probe-llm` из корня репозитория.
4. Посмотреть метаданные через `docker compose logs --tail=30 worker`: модель,
   версия промпта и расход токенов. Текст ответа и ключ не логируются.

Без ключа приложение запускается; LLM-probe завершается ошибкой до постановки
задания. Healthcheck не расходует квоту. Ключ не добавлять в Git, frontend или чат.
Probe отправляет только синтетический пример. Он проверяет формат ответа и ссылки,
но не качество смыслового вывода. Внешний вызов требует собственного API-ключа.

`OPENROUTER_TIMEOUT` — положительная длительность, например `180s` или `3m`.
`OPENROUTER_MAX_TOKENS` — положительное целое число, по умолчанию `8000`.
Недопустимые настройки вызывают ошибку запуска. Тайм-аут задания автоматически
равен тайм-ауту запроса + 20 секунд (по умолчанию 200 секунд), ожидание `probe-llm` —
тайм-ауту запроса + 60 секунд (240 секунд). Время ожидания включает очередь;
при большой очереди команда может завершиться раньше уже поставленного задания.
Обычная проверка Python сохраняет прежнее ожидание 90 секунд.
После изменения `.env` пересоздайте worker: `docker compose up -d --build worker`.
Верхнюю границу ответа также ограничивают возможности выбранной модели.

## Контракт и обработка ошибок

Вход: 1–10 требований `{id, text}`, 1–50 фрагментов `{id, text}`, до 64 KiB JSON.
Каждое требование получает один результат с `requirement_id`, `evidence` (список
`{source_id, quote}`),
`message`, `suggestion` и статусом:

- `met`: по оценке модели фрагменты подтверждают выполнение;
- `needs_review`: предлагается проверить конкретный пробел или противоречие;
- `insufficient_data`: предоставленных сведений недостаточно для вывода.

Схема — `services/backend/internal/modules/semantic/result.schema.json`, промпт —
`prompt_v2.txt` рядом с ней. Они встраиваются в бинарник через `go:embed`.
Go отклоняет неизвестные поля, пропущенные требования, ссылки на чужие фрагменты
и цитаты, которых нет в указанном источнике. Отклонённый ответ является технической
ошибкой модели, а не замечанием к документу. Проверка цитат не доказывает правильность вывода.
`context_complete` в требовании сообщает модели, передан ли весь релевантный контекст;
значение задаёт вызывающая система. Подробнее: [оценка и контракт v2](llm-evaluation.md).
Используются `response_format.type=json_schema`, `strict=true` и
`provider.require_parameters=true`. Если бесплатный endpoint не поддерживает
схему, запрос может завершиться ошибкой. Неполный ответ, отказ и неверный JSON
не считаются успехом.

Документ в промпте обозначен как недоверенные данные; инструменты модели не
предоставляются. Это не гарантия устойчивости к любым инструкциям внутри документа.
Для оценки нужен контрольный набор, включая ложные замечания, нечитаемые разделы
и попытки изменить инструкции модели через содержимое документа.
Начальный синтетический набор уже добавлен: `make eval-llm` выполняет 8 запросов
и сохраняет отчёт в `data/evaluations/latest.json`. Он не заменяет независимые
контрольные примеры и проверку специалистом.

HTTP 429 и временные сбои не запускают автоматическую серию обращений.
Параллелизм 1 не является лимитом запросов в минуту. После тайм-аута ожидания
команды уже поставленное задание может продолжить работу.

## Следующий этап

Пользовательский поток пока не подключён: нужны извлечение одного бланка, выбор
утверждённых требований, сохранение версий входа и результата в PostgreSQL,
отображение замечаний со ссылками на оригинал. Также нужны общий лимитер,
ограниченные повторы с учётом Retry-After и суточной квоты, кэш по версиям
входа/промпта/модели и статус «ИИ-проверка недоступна».
Перед отправкой реальных документов нужно определить допустимый состав данных
и условия обработки OpenRouter и конечным провайдером.
